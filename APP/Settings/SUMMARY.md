DELETE ACCOUNT — REAL SCOPE (#22)
------------------------------------------------------------

Real, hard deletion — `delete_own_account()` (SECURITY DEFINER,
20260726170000_delete_own_account.sql), verified end-to-end against a
scratch test account (not real seed data): deletes the auth.users row,
which cascades through profiles.id REFERENCES auth.users(id) ON DELETE
CASCADE and from there through every table referencing profiles(id) —
matches, conversations, messages, timelines, wali_links, wali_invites,
saves, likes, subscriptions, profile_photos, notifications,
onboarding_answers, journey_* tables. Also removes the user's actual
photo files from the `profile-photos` Storage bucket (client-side
Storage API call first, then a server-side path-prefix cleanup as a
second attempt — direct SQL DELETE on storage.objects is blocked by
Supabase's own protect_delete trigger unless explicitly bypassed,
which the function does via a scoped `storage.allow_delete_query`
setting).

Disclosed to the user in the confirmation dialog: deleting a Seeker's
account also deletes the OTHER party's copy of any shared Match/
conversation history (both sides of a match reference profiles(id) ON
DELETE CASCADE) — an unavoidable consequence of a real hard delete,
not withheld from the user.

Available to both Seeker and Guardian accounts (profile_screen.dart and
wali_profile_screen.dart both wire the same ZyraAuth.deleteAccount()).

now its own bottom-nav tab (see APP/Navigation/SEEKER NAVIGATION/

SIGN-IN & SECURITY — APPROVED MODEL
------------------------------------------------------------

The public app keeps Apple and Google as its two normal sign-in choices.
UPDATED 2026-08-29 under DR-ZYRA-219 items 4-5 (built as OA-ZYRA-277,
Fable-verified): Sign-in & Security shows ONLY the sign-in methods already
attached to the current account, as information — no "Add Apple/Google"
control exists and manual identity linking is OFF in V1. Linking may return
only through a separately approved change (authenticated + recently
re-authenticated session, corrected copy, post-link security notification).
A separately verified recovery email provides six-digit one-time-code
recovery with no ZYRA password and cannot create an account; the recovery
card may say "Add" when no recovery address exists — that is recovery setup,
not provider linking.

Provider identity, recovery email and contact/notification email are labelled
separately. Matching email text never causes an automatic account merge.

The Founder uses the same configured provider entry as every other account;
there is no public Founder/developer sign-in. Developer Access is unavailable
and denied at every entry/leaf in **ZYRA Production**
(`app.zyraconnect.zyra`); it is exposed only in the isolated
**ZYRA Test** target (proposed `app.zyraconnect.zyra.test`). ZYRA Test requires
a successful current staging-session refresh returning the independently
pinned exact Founder UUID with protected `app_metadata.zyra_role = founder`.
Neither condition alone, nor Workspace domain, email text, editable metadata,
TestFlight membership or build mode, grants access.
Sign-out clears refreshed Founder proof before the remote request and on every
completion/failure path.

Developer Access refreshes before navigation and again while its destination
is covered. Same-account/claim work joins one flight; account or claim changes
supersede older work. Every Auth event and app resume rechecks proof;
`userUpdated` and resume require a real refresh. Proof clears synchronously,
and non-refresh loss including `signedOut` immediately removes the open overlay
and guarded route through `AuthGate`. Direct Splash Lab menu/playback routes
repeat their own leaf guard. An Auth-stream error follows the same fail-closed
route and logs only a fixed generic diagnostic.

Both targets compile the same Settings and product implementation. Ordinary
UI/copy/logic changes therefore reach both by default; only app identity,
compile-time environment/backend configuration and protected test tooling may
differ without a new Founder ruling. ZYRA Test has no runtime backend selector
and cannot fall back to production. A missing or mixed staging configuration
fails closed before connection. The executable preflight exact-pins the
staging URL/reference/public client key, Google/native values, the exact
Founder UUID and all four persona UUIDs against deliberately unassigned
approved-resource pins. The five identity UUIDs must be unique, so it cannot
pass until an exact Founder-approved pin revision. It accepts only the
exact pinned `sb_publishable_*` value or exact pinned legacy JWT with anonymous
role and staging reference, rejecting secret/service-role, wrong-ref and
malformed keys. Configuration or startup failure stays on a Test-specific
lock/retry surface and never falls through to Welcome or Production.
On iOS, compiled flavour must also match the installed bundle/display identity
before Supabase starts; a mixed artifact locks and makes no connection.

The local target/backend/exact-Founder-UUID plus fresh-role scaffold exists
under OA-ZYRA-286. The

PRIVACY SCREEN — REAL SCOPE
------------------------------------------------------------

One genuinely-wired control: "Visible in Browse", toggling
`profiles.is_active` (the same column Browse's own discovery query
filters on, and that profiles_select RLS checks for row visibility).
Turning it off actually removes the Seeker from Browse for everyone
else — not cosmetic. No other privacy controls (blocking, photo
visibility rules, etc.) exist yet; the screen says so.
